# Neoantigen Vaccine Design Pipeline — Project Plan

## 1. Purpose

This application recreates the computational pipeline that real pharmaceutical companies (Moderna, BioNTech) use to design personalized mRNA cancer vaccines.

**The problem it solves:** When a person develops cancer, their tumor cells accumulate DNA mutations that healthy cells don't have. Some of those mutations change the proteins the tumor builds, creating "neoantigens" — protein fragments that exist only in cancer cells and nowhere else in the body. Because they're genuinely foreign, the immune system can be trained to attack them, hitting the tumor while sparing healthy tissue.

**What this app does:** Takes raw DNA sequencing data from a cancer patient (tumor tissue plus healthy tissue from the same person) and works through the full chain of analysis needed to identify which of that patient's specific mutations would make good vaccine targets — then outputs the actual mRNA sequence a lab would need to synthesize the vaccine.

**Scope boundary:** This is a computational design tool. It ends at producing a validated sequence file. Physically manufacturing that sequence into an injectable vaccine requires GMP-certified facilities, lipid nanoparticle formulation, and regulatory clearance — all outside this project. That handoff point (design → synthesis) is exactly where real bioinformatics teams hand off to wet labs.

**A note on accuracy expectations:** The final step of this pipeline (predicting whether a T cell will actually react to a given peptide) is the weakest link in the entire field. Across 25 institutions in the TESLA benchmark consortium, average precision for correctly identifying truly immunogenic neoantigens was roughly 7%, rising to ~50% only when ensembling multiple methods. This app is not expected to beat that — replicating state-of-the-art performance is the realistic bar.

## 2. Architecture Overview

Three layers, each doing what it's actually good at:

| Layer | Technology | Responsibility |
|---|---|---|
| **Frontend** | React (web app) | Dashboard UI, file upload, step navigation, sliders, results tables, toasts |
| **Orchestration** | C# / ASP.NET Core | REST API, job execution, filesystem validation, calling Python, error propagation |
| **Computation** | Python scripts + CLI bioinformatics tools | The actual scientific work (alignment, variant calling, HLA typing, binding prediction) |

**Why this split:** None of the real bioinformatics tools (MHCflurry, OptiType, pVACtools, BigMHC, GATK/Mutect2, bwa-mem2) exist in C#. They're Python packages or compiled binaries. Reimplementing them would be pointless and error-prone. So C# orchestrates and validates; Python executes; React presents.

### Data flow for a single step

```
User clicks "Run" in React
    ↓
POST /api/patients/{id}/steps/{stepName}/run
    ↓
C# controller → StepService for that step
    ↓
Service validates: do the required input files exist on disk?
    ↓ (if no) → return structured error → red toast
    ↓ (if yes)
Service invokes Python script as subprocess
    ↓
Python runs the actual tool, writes output files to that step's folder
    ↓
Python exits: code 0 + JSON summary, or nonzero + error message
    ↓
C# captures stdout/stderr, returns result
    ↓
React: green toast + refresh file table, or red toast with error text
```

## 3. Filesystem Design

This is the backbone of the whole app — state lives on disk, not in a database.

### Layout

```
/data
  /patients
    /{patientId}
      patient.json                 ← name, created date, notes
      /01_upload
      /02_alignment
      /03_variants
      /04_protein_effects
      /05_hla_typing
      /06_candidates
      /07_presentation
      /08_immunogenicity
      /09_filtering
      /10_ranking
      /11_vaccine_design
```

### Rules

1. **Each step owns exactly one folder.** A step writes only to its own folder.
2. **Each step reads from previous steps' folders.** Step 3 reads step 2's BAMs; it does not copy them.
3. **No file is ever overwritten or deleted.** New runs produce new timestamped files alongside old ones. Users can compare runs.
4. **The folder is the source of truth.** The file table in the UI is generated by listing the directory, not by querying a database. This means a user can manually drop a file into a folder and the app will see it — useful for debugging, for resuming interrupted work, and for using externally-generated files.
5. **Naming convention for generated files:** `{outputName}_{yyyyMMdd_HHmmss}.{ext}` so runs sort chronologically and never collide.

### Why no database (initially)

Patient metadata is small enough for a JSON file per patient. The heavy state is files, which live on disk anyway. Adding a database is a reasonable later refactor if you want run history, user accounts, or audit trails — but it's not needed for the core loop, and skipping it removes a whole layer of setup friction.

## 4. Backend Structure (C#)

```
/Backend
  /Controllers
    PatientsController.cs          ← CRUD for patients
    StepsController.cs             ← run a step, get step status, list files
  /Services
    /01_Upload
    /02_Alignment
    /03_VariantCalling
    /04_ProteinEffects
    /05_HlaTyping
    /06_CandidateGeneration
    /07_PresentationPrediction
    /08_ImmunogenicityPrediction
    /09_SafetyFiltering
    /10_Ranking
    /11_VaccineDesign
  /Common
    IPipelineStep.cs               ← shared interface
    PythonRunner.cs                ← subprocess wrapper
    FileSystemService.cs           ← path resolution, listing, validation
    StepResult.cs                  ← success/failure + message + output files
  /Python                          ← the actual scripts, called by services
```

### The shared step interface

Every step service implements the same contract, which makes the controller generic and makes adding steps trivial:

```csharp
public interface IPipelineStep
{
    string StepId { get; }              // "03_variants"
    string DisplayName { get; }         // "Call Mutations"
    string[] RequiredInputSteps { get; } // ["02_alignment"]

    ValidationResult ValidateInputs(string patientId);
    Task<StepResult> RunAsync(string patientId, StepParameters parameters);
}
```

`ValidateInputs` is the guard you described — it checks the previous step's folder actually contains what's needed before attempting anything, so the user gets "Step 2 output not found — run alignment first" instead of a cryptic Python traceback.

### Python invocation

`PythonRunner` handles: building the command, launching the process, streaming/capturing stdout and stderr, enforcing a timeout, and translating exit codes into `StepResult`. Python scripts communicate structured results back by printing a JSON blob to stdout on success; errors go to stderr and are surfaced verbatim in the red toast.

### Long-running steps

Alignment can take hours. Two options:

- **MVP:** synchronous request with a generous timeout, loading spinner on the button. Simple, works, blocks the UI tab.
- **Better:** fire-and-forget job with a status endpoint the frontend polls (`GET /api/patients/{id}/steps/{step}/status`). Same loading spinner, but survives page refresh and doesn't hold an HTTP connection open for two hours.

Recommend building the MVP synchronous version first, then upgrading to polling once the pipeline works end to end. The interface doesn't change — only the controller's handling of it does.

## 5. Frontend Structure (React)

### Page 1 — Patient Selection (landing page)

- Grid or list of existing patients, each showing name and progress indicator (which step they've reached)
- "Add Patient" button → modal for name/notes → creates the folder skeleton on disk
- Clicking a patient navigates to their dashboard

### Page 2 — Patient Dashboard

Three regions:

- **Top bar:** patient name, back-to-list link
- **Left sidebar:** the 11 steps as a vertical list. Each shows a status indicator (not started / has files / complete). Clicking selects the step.
- **Main panel:** content changes based on selected step.

### Main panel composition

Every step's panel is built from the same set of blocks, included or omitted as appropriate:

1. **Explanation block** (always) — plain-language description of what this step does and why, plus a line naming the tool used. Written to be accurate but readable by someone without a genetics background.
2. **Upload zone** (upload steps only) — one drop target per required file type, clearly labeled ("Tumor DNA", "Normal DNA", "RNA-seq (optional)")
3. **Parameter controls** (steps that have them) — sliders, toggles, numeric inputs
4. **Action button** (compute steps only) — "Run [step name]", shows spinner while executing
5. **Input files table** — what this step will read, pulled from prior step folders
6. **Output files table** — what's in this step's own folder: filename, size, created date, download link

### Toasts

Bottom-right, auto-dismiss after ~4 seconds:
- **Green:** step completed, with brief summary ("Called 487 variants")
- **Red:** failure, showing the actual error text from Python/C# — do not swallow or genericize these, the real error message is the most useful thing a user can see
- Consider making red toasts persist until dismissed, since errors are worth reading carefully

## 6. The Eleven Steps

For each: what it does, why it matters, the tool used, inputs, outputs, and UI specifics.

---

### Step 1 — Upload Sequencing Data
**Folder:** `01_upload`

**Explanation for the UI:**
> Every analysis starts with two DNA samples from the same person: one from their tumor, one from healthy tissue. Comparing them is what reveals which mutations belong to the cancer specifically, rather than being part of the person's normal inherited genetics. Optionally, you can also upload RNA sequencing data, which shows which genes the tumor is actually using — this improves target selection later but isn't required.

**Tool:** None (file intake only)

**Inputs:** User uploads
- Tumor DNA — FASTQ or BAM (required)
- Normal DNA — FASTQ or BAM (required)
- Tumor RNA-seq — FASTQ or BAM (optional)

**Outputs:** The uploaded files, stored as-is

**UI:** Three labeled upload zones. File table showing name, size, type, upload date. Large files (100GB+) are realistic here — the upload component needs chunked/resumable upload, or an alternative "point at a path on disk" mode for files too big to push through a browser.

**Note:** Given real WGS files run 140–240GB, browser upload may be impractical. Strongly consider supporting a "server-side path" input where the user specifies a location the backend can read directly.

---

### Step 2 — Align to Reference Genome
**Folder:** `02_alignment`

**Explanation for the UI:**
> Sequencing machines don't read DNA in order — they shatter it into millions of short fragments and read those. Alignment figures out where each fragment belongs on the human genome, like matching puzzle pieces to the picture on the box. If you uploaded BAM files, this step is already done and can be skipped.

**Tool:** `bwa-mem2` for DNA, `STAR` for RNA (RNA needs a different aligner because genes contain spliced-out sections that DNA aligners don't handle)

**Inputs:** FASTQ files from step 1, plus a reference genome (GRCh38)

**Outputs:** Sorted, indexed BAM files — one per sample

**UI:** Run button. Note in the explanation that BAM uploads skip this step. Possibly a reference genome selector if you want to support GRCh37 as well — but defaulting to GRCh38 only and stating so is simpler and safer, since mixing reference builds between tumor and normal breaks everything downstream.

---

### Step 3 — Call Somatic Mutations
**Folder:** `03_variants`

**Explanation for the UI:**
> This compares the tumor DNA against the healthy DNA from the same person and flags every position where they differ. Those differences are mutations that arose in the cancer specifically. The comparison against the person's own healthy tissue is essential — without it, you'd be flagging thousands of harmless inherited variations that every human has.

**Tool:** `Mutect2` (GATK)

**Inputs:** Tumor BAM + normal BAM from step 2

**Outputs:** VCF file listing somatic variants, PASS-filtered

**Key detail:** Mutect2 applies its own statistical confidence filter, marking calls as PASS or flagging them as likely artifacts. Only PASS calls should proceed. This is the noise filter — it accounts for read depth, base quality scores, strand bias, mapping quality, and a panel of normals (a database of recurring technical artifacts seen across unrelated samples). Expect a few hundred PASS variants for a typical tumor; melanoma runs higher (median ~489), lung cancer around 200.

**Also produced here:** Variant Allele Frequency (VAF) per mutation — the fraction of reads supporting each variant. This is *not* noise to discard; it reflects what fraction of tumor cells actually carry that mutation, and it feeds the clonality ranking in step 10.

**UI:** Run button. Output table should show variant count and possibly a VAF distribution histogram, which is genuinely informative about tumor heterogeneity.

---

### Step 4 — Determine Protein Consequences
**Folder:** `04_protein_effects`

**Explanation for the UI:**
> Not every DNA mutation matters. Only about 1–2% of the genome codes for proteins at all, and even within that, some mutations happen to produce the same amino acid as before — changing the DNA without changing the protein. This step translates each mutation into its protein-level effect and keeps only the ones that genuinely alter a protein, since those are the only ones the immune system could possibly notice.

**Tool:** `VEP` (Variant Effect Predictor)

**Inputs:** VCF from step 3

**Outputs:** Annotated VCF with consequence labels; filtered list of protein-altering mutations

**What survives:** missense (one amino acid swapped), nonsense (protein truncated), frameshift (insertion/deletion scrambling everything downstream — often a strong neoantigen source)
**What's discarded:** synonymous/silent mutations, and anything outside coding regions

**UI:** Run button. Output table showing counts by consequence type — a nice, immediately interpretable summary.

---

### Step 5 — HLA Typing
**Folder:** `05_hla_typing`

**Explanation for the UI:**
> HLA molecules are the display cases cells use to show the immune system samples of what they're building inside. Everyone inherits a specific set of HLA variants, and different variants physically hold different protein fragments — a target that works for one person may be invisible in another. This step reads the healthy DNA (HLA type is inherited, not caused by the cancer) to determine this patient's specific HLA variants.

**Tool:** `OptiType`

**Inputs:** Normal BAM/FASTQ from step 1 or 2

**Outputs:** JSON/text listing the patient's HLA class I alleles (e.g. HLA-A*02:01, HLA-B*07:02)

**UI:** Run button. Output displayed as a simple list of alleles — short, readable, and one of the more satisfying outputs to look at.

---

### Step 6 — Generate Candidate Peptides
**Folder:** `06_candidates`

**Explanation for the UI:**
> HLA display cases only hold short fragments — around 8 to 11 amino acids. Since we can't know exactly where the cell's internal machinery will cut a protein, this step generates every plausible short fragment containing each mutation, sliding a window across the mutated position. It also generates the matching unmutated version of each fragment, which is needed later to check how different the mutant version really looks to the immune system.

**Tool:** `pVACtools` (handles the windowing and wild-type pairing automatically)

**Inputs:** Annotated mutations from step 4, HLA alleles from step 5

**Outputs:** Candidate peptide list — mutant and wild-type pairs, each tagged with source mutation and HLA context

**Scale note:** Expect roughly 456 peptide-HLA evaluations per mutation (38 sliding windows × ~6 HLA alleles × 2 for mutant/wild-type). A 500-mutation melanoma produces around 228,000 pairs.

**UI:** Run button. Output table showing candidate count, plus a preview of the first N peptides.

---

### Step 7 — Predict HLA Presentation
**Folder:** `07_presentation`

**Explanation for the UI:**
> This predicts which candidate fragments will actually be displayed on this patient's HLA molecules. A fragment that can't physically fit the display case will never be seen by the immune system, no matter how foreign it looks. Roughly half to three-quarters of the top-ranked predictions here turn out to be genuinely displayed.

**Tool:** `MHCflurry 2.0` (primary — fast, open source, runs on CPU) with optional `BigMHC-EL` as a second opinion

**Inputs:** Candidate peptides + HLA alleles

**Outputs:** Scored, ranked candidate list

**Performance note:** MHCflurry handles ~7,000 predictions/second — a full 228,000-pair melanoma workload takes well under a minute on a laptop. This step is cheap.

**UI:** Run button. Optional toggle for which predictor(s) to use. Results table sorted by score.

---

### Step 8 — Predict Immunogenicity
**Folder:** `08_immunogenicity`

**Explanation for the UI:**
> Being displayed isn't the same as being noticed. Most displayed fragments never provoke an immune response. This step predicts which ones will actually attract T cells — and it's the least reliable part of the whole pipeline. Current tools score only modestly better than chance, and this is an open research problem across the entire field, not a limitation of this app specifically.

**Tool:** `BigMHC-IM` (or PRIME / PepFore as alternatives)

**Inputs:** Presentation-scored candidates from step 7

**Outputs:** Re-scored, re-ranked candidate list

**Honesty note for the UI:** State the roughly 10–35% precision expectation directly. Users should not walk away thinking these predictions are reliable — the value is in *ordering* candidates better, not in certainty about any individual one.

**UI:** Run button, optional predictor selector, results table.

---

### Step 9 — Safety and Expression Filtering
**Folder:** `09_filtering`

**Explanation for the UI:**
> Two filters here. First, safety: if a candidate fragment closely resembles a normal human protein, targeting it risks the immune system attacking healthy tissue — those are removed. Second, if RNA data was provided: mutations in genes the tumor isn't actually using are removed, since a gene that's switched off produces no protein and therefore no target.

**Tool:** Reference proteome comparison (UniProt/Ensembl) for self-similarity; RNA-seq read counts (Salmon or STAR quantification) for expression

**Inputs:** Ranked candidates from step 8; optional RNA-seq quantification

**Outputs:** Filtered candidate list, plus an audit log of what was removed and why

**UI:** Run button. Toggle for whether to apply the expression filter (disabled/greyed if no RNA-seq was uploaded — the UI should make it obvious *why* it's unavailable rather than silently ignoring it). Table of removed candidates with removal reasons is genuinely useful for understanding what happened.

---

### Step 10 — Weighted Final Ranking
**Folder:** `10_ranking`

**Explanation for the UI:**
> The final ranking combines several signals, and you can control how much each one matters. Binding strength difference (agretopicity) measures how much more strongly the mutated fragment binds compared to its normal counterpart — a bigger gap means it looks more foreign. Expression is how actively the gene is used. Clonality is what fraction of tumor cells carry the mutation — targeting a mutation present in every cell is safer than one present in only some. HLA spread means deliberately choosing targets across different HLA types, so the tumor can't escape by losing just one.

**Tool:** Custom scoring logic (this is your own code — the interesting part)

**Inputs:** Filtered candidates from step 9

**Parameters (sliders, 0–1 weight each):**
- Agretopicity weight
- Expression weight (disabled without RNA-seq)
- Clonality weight (driven by VAF from step 3)
- HLA spread weight

**Outputs:** Final ranked list; top 20–34 flagged as selected

**Design consideration:** HLA spread is a *set-level* property, not a per-candidate score — you can't score one peptide's "spread" in isolation. Implement it as a diversity constraint during selection (e.g. greedy selection that penalizes picking another peptide restricted to an already well-covered allele) rather than as a simple additive weight.

**UI:** Four sliders, live-updating ranked table showing how the order shifts as weights change. This is the most interactive and most satisfying screen in the app.

---

### Step 11 — Design Vaccine Sequence
**Folder:** `11_vaccine_design`

**Explanation for the UI:**
> This assembles the final selected targets into a single mRNA sequence — the actual blueprint a lab would synthesize. The chosen fragments are strung together with short connector sequences between them, wrapped in standard start and end elements that help cells read the instructions properly. The output is a sequence file, not a physical vaccine; manufacturing requires specialized facilities and regulatory approval.

**Tool:** `pVACvector`

**Inputs:** Selected top candidates from step 10

**Outputs:** FASTA file containing the full construct

**Construct anatomy** (worth showing visually in the UI):
```
[5' cap] — [5' UTR] — [signal peptide] — [neoantigen 1] — [linker] — [neoantigen 2] — [linker] — ... — [3' UTR] — [poly-A tail]
```

**Why pVACvector specifically:** stringing peptides together creates *new* sequences at the junctions between them, which can themselves accidentally bind HLA — wasting immune attention or creating unintended targets. pVACvector optimizes the ordering and spacing to avoid generating problematic junctional epitopes.

**Expected construct size:** roughly 1,300–1,500 base pairs for 20–34 neoantigens.

**UI:** Run button, plus a prominent Download/Export button for the FASTA. Consider also offering a GenBank-format export, which supports labeled feature annotations so the file self-documents which region is which — much more useful than a bare wall of letters.

## 7. Testing Strategy

### The core problem and the solution

Real inputs to this pipeline are 140–240GB per file. You have ~10GB free. This is not a blocker, because genomics has a well-established practice of **subsetting to a single small chromosome** — the tools behave identically on chr21 (46Mb, the smallest human autosome) or chr22 as they do on the full genome, they just finish in seconds instead of hours.

Every step below has a **Tier 1 test** (runs on your Mac now, under 500MB total) and a **Tier 2 test** (full-scale, for the server later). Build against Tier 1; Tier 2 is written now and run when you have hardware.

### Test data budget

| Asset | Size | Purpose |
|---|---|---|
| chr21 reference FASTA + bwa index | ~250MB | All alignment/calling tests |
| Synthetic tumor FASTQ (chr21 subset, 30x) | ~40MB | Steps 2–3 |
| Synthetic normal FASTQ (chr21 subset, 30x) | ~40MB | Steps 2–3 |
| Pre-made VCF fixtures | <1MB | Steps 4, 6, 10 |
| Peptide list fixtures (JSON/TSV) | <1MB | Steps 6–11 |
| HLA reference (OptiType bundled) | ~20MB | Step 5 |
| **Total** | **~350MB** | |

### Generating the test data

Do not download real data for testing. Generate it:

```bash
# 1. Pull just chr21 from UCSC (~46MB gzipped, ~12MB after)
wget https://hgdownload.soe.ucsc.edu/goldenPath/hg38/chromosomes/chr21.fa.gz

# 2. Index it (bwa-mem2 index adds ~200MB for chr21 alone)
bwa-mem2 index chr21.fa

# 3. Simulate paired-end reads with known, planted mutations
#    Tools: wgsim (bundled with samtools), ART, or NEAT
wgsim -N 500000 -r 0.001 chr21.fa normal_R1.fq normal_R2.fq
wgsim -N 500000 -r 0.001 -R 0.15 chr21.fa tumor_R1.fq tumor_R2.fq
```

**Why this is better than real data for testing:** simulators write out a truth file listing exactly which mutations they planted. You can assert your pipeline finds them — impossible with real data, where you don't know the answer.

### The testing interface

Build a **test harness page** in the React app, at `/dev/tests`, gated behind a config flag so it doesn't ship to a real deployment.

```
┌─ Pipeline Test Harness ────────────────────────┐
│  [Seed Test Patient]  [Run All]  [Clear]       │
│                                                 │
│  Step                    Tier 1    Tier 2       │
│  01 Upload               ✓ 0.2s    ⊘ skipped   │
│  02 Alignment            ✓ 12s     ⊘ skipped   │
│  03 Variant Calling      ✓ 8s      ⊘ skipped   │
│  04 Protein Effects      ✗ FAIL    ⊘ skipped   │
│     └ Expected 12 missense, got 0              │
│        VEP cache not found at /refs/vep        │
│  ...                                            │
└─────────────────────────────────────────────────┘
```

Backing this: `POST /api/dev/tests/run?tier=1&step=03`. Each step service gains a companion test class. "Seed Test Patient" creates a patient whose folders are pre-populated with fixtures — meaning you can jump straight to testing step 8 without running steps 1–7.

**This fixture-seeding is the single most valuable testing feature.** It decouples every step from every other step.

### Three layers of tests

**Layer 1 — Unit tests (C#, xUnit).** No Python, no bioinformatics tools, no files over a few KB. Test: path resolution, `ValidateInputs` logic, `StepResult` parsing, ranking math, error propagation. These should run in under 5 seconds total and cover the majority of your actual C# code.

**Layer 2 — Integration tests (per step).** C# invokes real Python invoking real tools, against Tier 1 fixtures. Verifies the subprocess boundary actually works — this is where most real bugs live (wrong working directory, missing env var, tool not on PATH, stdout parsing breaking on an unexpected warning line).

**Layer 3 — End-to-end.** Full chr21 pipeline, step 1 through 11, asserting a FASTA comes out the other end. Slow-ish (minutes) but the only thing that proves the whole chain holds together.

---

### Per-step test specifications

---

**Step 1 — Upload**

*Tier 1:* Upload 1KB dummy files with `.fastq`, `.bam`, `.txt` extensions. Assert: valid extensions accepted, `.txt` rejected with clear message, files land in `01_upload/`, file table lists them with correct sizes, duplicate upload doesn't overwrite.

*Tier 2:* 200GB file via server-side-path mode. Assert no OOM, no timeout, correct size reported.

*Mock strategy:* None needed — this step has no computation.

---

**Step 2 — Alignment**

*Tier 1:* chr21 synthetic FASTQs (~80MB). Assert: BAM produced, `samtools quickcheck` passes, index file exists, >95% of reads mapped (simulated reads from the same reference should align nearly perfectly — a low rate means something's broken), runtime under ~60s.

*Tier 2:* Full HG008 tumor/normal WGS. Assert completion, mapping rate, runtime within budget.

*Mock strategy:* Add a `--dry-run` flag to the Python wrapper that validates arguments and emits a stub BAM without invoking bwa-mem2. Lets you test C#-side orchestration on a machine where the tools aren't installed.

*Storage note:* the bwa-mem2 index for chr21 is the bulk of your test data footprint (~200MB). Build it once, keep it, never regenerate.

---

**Step 3 — Variant Calling**

*Tier 1:* The two chr21 BAMs from step 2. **Assert against the simulator's truth file** — wgsim outputs planted mutation positions, so you can compute real recall and precision. Expect >80% recall of planted variants; investigate if much lower. Also assert: VCF is valid (`bcftools view` parses it), PASS-filtered subset is non-empty, VAF field is populated on every record.

*Tier 2:* Full genome. Assert variant count lands in a plausible range (hundreds to low thousands for HG008; a count of 50,000 means something's misconfigured, likely the normal sample wasn't used).

*Mock strategy:* Ship a hand-written 20-line VCF as a fixture. Every downstream step's Tier 1 test starts from this, not from actually running Mutect2.

*Gotcha to test explicitly:* run Mutect2 without a matched normal and assert it fails loudly rather than silently producing garbage — this is a mistake that's easy to make and produces plausible-looking wrong output.

---

**Step 4 — Protein Consequences**

*Tier 1:* Hand-crafted VCF with one mutation of each known type, where you've manually verified the expected consequence:
- A synonymous variant → must be filtered out
- A missense variant → must survive, correct amino acid change reported
- A nonsense variant → must survive, flagged as stop-gained
- A frameshift indel → must survive, flagged as frameshift
- An intergenic variant → must be filtered out

This is a **golden-file test** — the strongest kind available here, because the correct answer is knowable by hand from the genetic code.

*Tier 2:* Full VCF from step 3. Assert consequence-type distribution is biologically plausible (roughly, missense should outnumber nonsense by a wide margin).

*Mock strategy:* VEP's cache is large (several GB) — this is your one Tier 1 storage risk. Use VEP in `--database` mode (queries Ensembl remotely, no local cache, slower but ~0 storage) for local testing, and cache mode on the server.

---

**Step 5 — HLA Typing**

*Tier 1:* OptiType ships with test data — use it. Assert: output contains 6 class I alleles (2 each of A, B, C), format matches `HLA-A*02:01` pattern, parser handles it correctly.

*Tier 2:* HG008 normal sample. Assert 6 alleles, all valid against the IMGT/HLA allele list.

*Mock strategy:* Fixture file containing a known HLA set. Steps 6–11 tests should use this fixture rather than running OptiType.

---

**Step 6 — Candidate Generation**

*Tier 1:* Pure logic test, no external tools — this is your own sliding-window code and it's fully unit-testable. Given a 20-amino-acid protein with a known mutation at position 10, assert:
- Correct number of windows generated for lengths 8, 9, 10, 11
- Every generated peptide actually contains the mutated position
- A wild-type counterpart exists for every mutant peptide, same length, same position
- Mutations near the protein's start/end produce fewer windows without crashing (boundary condition — this is where off-by-one bugs live)

*Tier 2:* Full mutation set. Assert candidate count is roughly `mutations × 38 × alleles × 2`, matching the expected scale.

*Mock strategy:* None needed — no external dependency.

---

**Step 7 — Presentation Prediction**

*Tier 1:* MHCflurry on ~100 peptides. Assert: every peptide gets a score, scores are in valid range, known strong binders (use published HLA-A*02:01 epitopes as positive controls — e.g. well-characterized influenza or CMV epitopes) score better than random sequences. Runtime under 10s.

*Tier 2:* Full 228k-pair workload. Assert completion under a minute, memory stays reasonable.

*Mock strategy:* A stub predictor returning deterministic pseudo-random scores, for testing the ranking/UI layers without invoking the model.

*Positive-control test is important here* — it catches the case where the tool runs successfully but is misconfigured (wrong allele format, peptides passed in wrong column) and returns meaningless scores.

---

**Step 8 — Immunogenicity Prediction**

*Tier 1:* Same shape as step 7 — small peptide set, assert scores populated and in range. **Do not assert on accuracy.** The tool is genuinely only modestly better than chance; a test asserting "immunogenic peptides score higher" will be flaky and will teach you nothing.

*Tier 2:* Full candidate set, assert completion and GPU/CPU fallback works.

*Mock strategy:* Stub predictor, same as step 7.

---

**Step 9 — Safety and Expression Filtering**

*Tier 1:* Two targeted tests.
- *Self-similarity:* feed in a peptide taken verbatim from a known human protein (e.g. a hemoglobin fragment) alongside genuinely novel sequences. Assert the human-derived one is removed and the novel ones survive.
- *Expression:* feed a candidate list plus a small hand-made expression table where one gene has zero expression. Assert that candidate is removed and others survive. Then run with expression data absent and assert the filter is skipped cleanly rather than crashing or silently zeroing everything.

*Tier 2:* Full proteome comparison, full RNA-seq quantification.

*Mock strategy:* A 50-protein mini-proteome FASTA instead of full UniProt (which is ~100MB+). Sufficient to prove the matching logic works.

---

**Step 10 — Weighted Ranking**

*Tier 1:* This is pure math on your own code — test it hard, it's cheap.
- Set one slider to 1.0 and the rest to 0. Assert the ranking matches sorting by that single criterion alone.
- Set all sliders to 0. Assert graceful behavior (stable order, no divide-by-zero).
- Assert changing a weight actually reorders the list.
- Assert exactly N candidates are selected when asked for N.
- *HLA spread specifically:* construct a candidate set where the top 30 by raw score all bind one allele, and lower-scoring candidates cover other alleles. Assert that with spread weight high, the selection includes multiple alleles. This is the trickiest logic in the app and deserves its own dedicated test.

*Tier 2:* Real candidate set, assert ranking completes and selection is sane.

*Mock strategy:* Synthetic candidate list with hand-assigned scores — full control over the expected answer.

---

**Step 11 — Vaccine Design**

*Tier 1:* 5 short peptides through pVACvector. Assert: FASTA is valid and parseable, contains all input peptides, linkers present between them, UTRs present, total length plausible. Also assert the export/download endpoint returns correct content-type and filename.

*Tier 2:* Full 20–34 peptide construct. Assert length in the 1,300–1,500bp range, and that pVACvector's junctional epitope check actually ran.

*Mock strategy:* Simple concatenation stub for testing the download/export UI without invoking pVACvector.

### Tool availability and graceful degradation

Not all tools will be installed on your Mac (GATK needs Java, bwa-mem2 may need building, VEP is heavy). Handle this explicitly rather than letting tests fail confusingly:

- Every step service exposes a `CheckToolAvailability()` method
- The test harness runs this first and marks unavailable steps as **SKIPPED (tool missing)** — visually distinct from FAILED
- The dashboard shows a tool-status panel so you can see at a glance what's runnable in your current environment

This means you can develop the entire UI, orchestration layer, ranking logic, and steps 6/10/11 on your Mac with essentially zero storage, and only the alignment-heavy steps require a real environment.

### Recommended local development configuration

Given ~10GB free:

- **Install and test locally:** MHCflurry (pip, ~200MB with models), your own step 6 and 10 logic, pVACtools
- **Stub locally, test on server:** bwa-mem2, Mutect2/GATK, VEP with cache, OptiType
- **Total local footprint:** roughly 600MB–1GB including test fixtures

That's enough to prove the architecture works end to end with stubs in place, which is exactly the "basic validation this will work" bar you're aiming for.

## 8. Cross-Cutting Concerns

### Error handling
Python scripts must fail loudly and specifically. A missing reference genome, a malformed VCF, an out-of-memory kill — each should produce a distinct, readable message that reaches the user's toast unmodified. Generic "Step failed" messages waste the user's time.

### Validation before execution
Every service checks preconditions before spending compute: do input files exist, are they non-empty, are they the expected format, is the required tool installed and on PATH. Fail fast with a clear message.

### Compute and storage reality
- WGS BAM files: 140–240GB each. Disk space checks before writing are worth adding.
- Alignment: hours, potentially. RAM in the 16–32GB range.
- MHCflurry/BigMHC: seconds to minutes. Trivial by comparison.
- The heavy steps (2 and 3) are likely to run on a rented remote machine rather than a laptop. Design shouldn't assume local-only.

### Configuration
A single config file (appsettings + a Python config) holding: reference genome path, tool paths/binaries, Python environment location, data root directory, timeouts. Hardcoded paths will cause pain the moment this moves to a different machine.

### Validation against ground truth (stretch goal)
The TESLA dataset (Synapse `syn21048999`) contains patient-matched tumor/normal sequencing plus experimentally confirmed immunogenic and non-immunogenic peptides. Running the full pipeline against a TESLA patient and comparing your top-ranked candidates to the confirmed labels gives a real, measured precision number for your own pipeline — a far stronger project result than citing published benchmarks. Access requires a free Synapse account plus certification quiz.

**Note on the primary dataset:** GIAB HG008 (NIST) is fully open, no access application — a real PDAC tumor cell line with matched normal duodenal and pancreatic tissue from the same consented patient. FTP: `https://ftp.ncbi.nlm.nih.gov/ReferenceSamples/giab/data_somatic/HG008/`

## 9. Suggested Build Order

Working end-to-end early beats building each step perfectly in sequence.

1. **Skeleton first** — React shell, C# API, patient CRUD, folder creation, one dummy step that just lists files. Prove the whole loop works.
2. **Steps 5–8 next** (HLA typing → candidates → presentation → immunogenicity). These are fast, cheap, testable, and where the interesting logic is. You can feed them small hand-made inputs while building.
3. **Steps 9–11** — filtering, ranking sliders, vaccine design. Completes the interesting half.
4. **Steps 2–4 last** (alignment, variant calling, protein effects). These are slow, resource-hungry, and mostly just wrapping existing tools. Until they're built, feed the pipeline a pre-made VCF so downstream steps have real input.
5. **Step 1 upload handling** — likely needs the server-side-path approach for realistic file sizes; worth solving once the rest works.

**Build the test harness in phase 1, not last.** The fixture-seeding capability ("create a patient with steps 1–7 pre-populated") is what makes phases 2–3 practical on a low-storage machine. Without it, testing step 8 means running steps 1–7 first, which you can't do locally. With it, every step is independently developable.

## 10. Open Questions

Worth deciding before or during implementation:

1. **Multi-user?** Currently designed single-user, no auth. Adding accounts changes the folder layout (`/data/users/{userId}/patients/...`) and adds real security requirements — much easier to decide now than retrofit.
2. **Where does compute run?** If steps 2–3 run on a remote machine, does the C# backend also live there, or does it dispatch remotely? Simplest: run the whole backend on the compute machine, access the React app over the network.
3. **Reference genome distribution** — GRCh38 plus indexes is ~30GB+. Bundled, downloaded on first run, or user-supplied path?
4. **Tool installation** — Docker containers per tool is the clean answer (bioinformatics dependency management is notoriously painful) but adds setup complexity. Conda environments are the lighter alternative.
5. **Run comparison UI** — since files are never overwritten, multiple runs accumulate. Is there a UI for comparing them, or is it just a file list?
6. **Real patient data handling** — if this ever touches non-public patient data, access controls and data handling policies become a genuine requirement, not an optional feature.
